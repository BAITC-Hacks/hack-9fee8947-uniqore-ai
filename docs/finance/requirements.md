# Условия кейса «Граф денег»

Это **структурированный пересказ условий**, а не новое ТЗ и не отчёт о готовности решения. При расхождениях первичен [исходный PDF кейса](sources/case.pdf). Схемы и параметры предоставленных данных описаны в [README датасета](sources/data-description.md).

## 1. Задача и пользователь

Название кейса: «Граф денег: восстановление финансовой структуры организованной группы по транзакционной сети». Формат, указанный в ТЗ: командная разработка за пять часов. Это описание формата соревнования, а не утверждение об оставшемся времени.

Основной пользователь — AML-аналитик или специалист финансового мониторинга банка второго уровня. По исходному списку из 81 клиента он должен получить модель наблюдаемой сети: участников, связи, направление переводов, роли, кластеры и обоснованный порядок проверки.

Требуется аналитический инструмент: **расчётный пайплайн и интерфейс просмотра**. Главный вопрос: «Кого из 2 248 клиентов проверить первым и почему?». Результат помогает формировать гипотезы для углублённой проверки; он не устанавливает виновность клиентов.

## 2. Входные данные и границы наблюдения

Вход — три предоставленных организаторами файла Parquet. Обработка пакетная; онлайн-поток не требуется. Архив с папкой `data/` выдаётся командам в начале хакатона; внешние источники не требуются и не предоставляются.

| Файл | Объём | Содержание |
|---|---:|---|
| `edges.parquet` | 3 119 строк | Уникальные направленные пары плательщик → получатель, агрегированные за период: `src, dst, sum_kzt, n_tx, depth` |
| `nodes.parquet` | 2 248 строк | Узлы: `gid, depth, is_seed` |
| `transactions.parquet` | 4 840 строк | Отдельные транзакции: `src, dst, date, sum_kzt` |

Параметры сбора:

- 81 стартовый клиент, обозначенный `is_seed`.
- Период: 1–31 июля 2026 года.
- Только внутрибанковские переводы; обход только по исходящим связям на четыре колена.
- Транзакции меньше 5 000 KZT не включены.
- Новые узлы по глубине: seed — 81; первое колено — 472; второе — 462; третье — 789; четвёртое — 444.
- Указанный в ТЗ суммарный оборот графа: 365 890 012 KZT. Это характеристика предоставленного набора, а не метрика качества решения.

Ограничения, которые необходимо учитывать:

| Ограничение | Следствие для анализа |
|---|---|
| 444 узла находятся на четвёртом колене и не имеют наблюдаемых исходящих связей | Нельзя автоматически считать их настоящими конечными получателями: это может быть граница обхода |
| Обход идёт только по исходящим переводам | Входящие потоки из-за пределов выборки не видны; полный баланс клиента восстановить нельзя |
| Входящие суммы seed неполны | Отношение исходящих сумм к входящим нельзя интерпретировать без оговорок; в ТЗ отмечены 354 узла, отправивших больше наблюдаемого входа |
| Порог 5 000 KZT | Дробление переводов ниже порога не наблюдается |
| 19 из 81 seed отсутствуют в рёбрах; ещё 12 представлены только как получатели | 31 seed не имеет наблюдаемых исходящих переводов; узлы без рёбер также должны попасть в результат |
| В ТЗ для графа по рёбрам указаны 16 слабосвязных компонент; вне крупнейшей — 352 узла | Нельзя анализировать только крупнейшую компоненту; 19 узлов без рёбер необходимо учитывать дополнительно |
| Нет атрибутов клиента | Не известны ФИО, возраст, тип операции и остатки; доступны структура и суммы переводов |
| Нет размеченных ролей — ground truth | Оценка опирается на обоснованность критериев, а не на accuracy по отсутствующей разметке |

Уточнение области подсчёта: 16 компонент и 352 узла вне крупнейшей относятся к 2 229 узлам, встречающимся в рёбрах. После добавления всех 19 изолированных seed полный граф из 2 248 узлов содержит 35 слабосвязных компонент. Это пояснение к пересказу; исходный PDF сохранён без изменений.

**Права и приватность:** по ТЗ данные обезличены; `gid` — синтетический идентификатор без привязки к личности. Данные предоставлены исключительно для использования в рамках хакатона. Это условие не является разрешением на иное использование или распространение исходного датасета. В этом документационном пакете описан входной контракт; сами Parquet-файлы не включены.

## 3. Пять обязательных требований

Без этих пяти пунктов решение по ТЗ не считается выполненным.

| № | Что обязательно | Как проверяет жюри |
|---|---|---|
| 1 | Воспроизводимый пайплайн: один запуск от исходных Parquet до всех трёх CSV, без ручных шагов | Команда из README запускается на чистой машине, создаёт три файла и отрабатывает менее чем за пять минут |
| 2 | Роль и скор каждого узла: все 2 248 узлов получают `role`, `role_score`, `evidence` | В `nodes_roles.csv` ровно 2 248 строк; обязательные поля заполнены, объяснения не пустые |
| 3 | Документированные и объяснимые критерии ролей: формальное правило либо метрика с порогом для каждой роли | Жюри называет три произвольных `gid`; команда за минуту объясняет назначенные роли, опираясь на свои метрики |
| 4 | Кластеризация: узлы разделены на группы; для каждой указаны размер, число seed, оборот и гипотеза | Заполнен `clusters.csv`; у каждого узла есть `cluster_id` в `nodes_roles.csv` |
| 5 | Ранжированный список не менее 20 узлов с обоснованиями и визуализация сети с направлениями, ролями и кластерами | Заполнен `top_nodes.csv`; по названному `gid` команда находит узел на схеме и показывает его связи |

Общий раздел ТЗ указывает задержку «не более пяти минут», а таблица проверки первого обязательного пункта — «менее пяти минут». Для прохождения обеих формулировок полный пересчёт должен занимать **менее 300 секунд** на предоставленном объёме, локально на обычном ноутбуке.

## 4. Выходные файлы и интерфейс

Нужны три CSV фиксированной схемы и экран просмотра. Формат интерфейса свободный: веб-страница, ноутбук или desktop-приложение. На экране должны быть направления потоков, роли, кластеры и поиск по `gid`.

### `nodes_roles.csv`

Одна строка на каждый из 2 248 узлов.

| Поле | Тип по ТЗ | Значение |
|---|---|---|
| `gid` | `int64` | Идентификатор клиента |
| `role` | `str` | Основная роль из документированного словаря |
| `role_score` | `float` | Уверенность в роли, от 0 до 1 |
| `cluster_id` | `int` | Номер кластера |
| `priority_score` | `float` | Приоритет проверки для аналитика, от 0 до 1 |
| `evidence` | `str` | Человекочитаемое объяснение назначения роли, не более 200 символов |

Роль должна объясняться метриками и порогами. Значение `role_score` и способ его расчёта также необходимо пояснить; сам диапазон 0–1 не доказывает статистическую калибровку уверенности.

### Обязательный минимум словаря ролей

Команда вправе расширить словарь, задокументировав дополнительные роли.

| Роль | Смысл по ТЗ |
|---|---|
| `consolidator` | Точка консолидации: аккумулирует средства от нескольких участников |
| `transit` | Транзитный счёт: пропускает средства дальше, не удерживая |
| `distributor` | Веерно распределяет средства множеству получателей |
| `terminal` | Конечный получатель: деньги приходят и остаются |
| `coordinator` | Координирующий узел, кандидат в организаторы |
| `peripheral` | Периферия: признаков другой роли не выявлено |

Это определения ролей, а не готовые правила классификации. Команда определяет и объясняет свои критерии. Выводы о клиентах остаются гипотезами с учётом неполноты наблюдений.

### `clusters.csv`

Одна строка на кластер; обязательные поля:

```text
cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis
```

Нужно указать размер кластера, число seed, внутренний оборот, ключевые узлы и текстовую гипотезу о назначении. Принадлежность каждого узла кластеру отражается в `nodes_roles.csv`.

### `top_nodes.csv`

Ранжированный список **не менее 20 узлов**; обязательные поля:

```text
rank,gid,role,priority_score,why
```

`why` — текстовое обоснование приоритета. Каждая позиция списка должна быть понятна аналитику без подготовки в машинном обучении.

## 5. Дополнительные возможности

По ТЗ эти возможности могут дать дополнительные баллы, но их отсутствие не блокирует сдачу. Отдельные численные веса для них не установлены.

- Учёт обрыва графа: обоснованное отделение гипотез о конечных получателях от последствий границы четвёртого колена.
- Временные паттерны: вход и выход через один-два дня, всплески активности, синхронные переводы нескольких плательщиков за день.
- Повторяющиеся маршруты и возвратные потоки: устойчивые цепочки и циклы.
- Аномалии: дробление сумм и отличия профиля узла от других узлов его колена; допустимы правила или ML-модель.
- Устойчивость сети: анализ того, что произойдёт при изъятии top-N узлов и распадётся ли граф на изолированные фрагменты.
- AI-ассистент: вопрос на естественном языке и ответ по графу со ссылками на узлы.
- Автоматическая карточка узла: роль, потоки, связи и основания для внимания.
- Оценка полноты: каких данных не хватает и какой запрос может сделать аналитик дальше.

## 6. Ограничения реализации

Запрещено:

- Хардкодить списки `gid` под «правильный ответ» вместо расчёта.
- Выдавать роль без объяснимого правила или интерпретируемых признаков — «чёрный ящик» не закрывает обязательный пункт 3.
- Обогащать данные внешними источниками или добавлять вымышленные атрибуты клиентов, например пол, возраст, доход или организацию.
- Требовать облачный кластер, GPU-обучение или платные сервисы для воспроизведения результата.

Обязательно:

- Обосновывать каждую роль и каждую позицию top-листа понятным аналитику языком.
- Работать с обезличенными данными, без ФИО, ИИН и иных персональных сведений.
- Формулировать выводы как гипотезы для проверки, а не утверждения о виновности.
- Выполнять расчёт локально на обычном ноутбуке. Интернет может требоваться только для внешнего LLM API, если команда его использует; это не отменяет запрета обязательной платной зависимости для воспроизведения результата.
- В README текстом объяснить, что изменится в подходе при росте графа примерно до одного миллиона узлов. Реализация такого масштаба не требуется.

Язык и библиотеки не ограничены. В ТЗ рекомендуется Python с pandas и NetworkX/igraph; в исходном пакете кейса организаторы предоставляют папку `starter/` с загрузкой, сборкой графа, базовыми метриками и шаблонами выгрузок. Рекомендация стека не делает его обязательным.
