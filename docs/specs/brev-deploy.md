# Конфигурация деплоя Tyuin на NVIDIA Brev

## Задача и границы

Как участник команды, я хочу развернуть Tyuin на NVIDIA Brev из конфигурации репозитория, чтобы показывать работающий интерфейс без ручной настройки Python.

Первоначальная ветка: `codex/brev-deploy`, база проверки: `18c412d`; затем объединена с `main` `0b5e0ba` и слита через PR #16. Продолжение с публичным доменом подготовлено в `codex/brev-public-domain` от `main` `6620aa1`. Первоначальный объём: контейнеризация существующего приложения и инструкция. 23.09.2026 пользователь дополнительно разрешил создание платной CPU VM `tyuin`, развёртывание приложения на Brev и публичный доступ к демонстрационным данным, API и CSV без авторизации. Сначала проверен доступ через ngrok, затем по выбору пользователя приложение опубликовано напрямую на собственном домене `hackalemai.uniqore.dev`; туннель ngrok остановлен. Публикация образа в реестр в выполненный объём не входит.

## Решение

- Python 3.12, зависимости из `requirements.lock`, готовый frontend из `moneygraph/web/` и три исходных Parquet входят в образ.
- Один процесс `python -m moneygraph demo` пересчитывает данные, проверяет CSV и запускает API с интерфейсом на порту 8765. GPU и внешний LLM не обязательны.
- Контейнер работает без root, проверяется через `/api/health`, результаты сохраняются в Docker volume. При перезапуске выполняется новый расчёт.
- Корневой Compose собирает образ из checkout; отдельный Compose для Brev запускает заранее опубликованный образ без локального build context.
- Секреты приложения задаются окружением. Контекст сборки ограничен явным списком файлов. Доступ возможен через SSH или публичный HTTPS на собственном домене; собственной авторизации у приложения нет.
- `deploy/brev/domain-web.compose.yml` и `deploy/brev/caddy/Caddyfile` добавляют Caddy для прямого HTTPS на `hackalemai.uniqore.dev` с сертификатом Let's Encrypt и перенаправлением HTTP на HTTPS. Прокси обращается к приложению через loopback; named volumes `caddy-data` и `caddy-config` сохраняют данные сертификатов и конфигурацию в `/data` и `/config`.
- `deploy/brev/public-web.compose.yml` сохраняет ранее проверенный вариант с отдельным контейнером ngrok и обязательным закреплённым доменом; сейчас этот туннель остановлен. Конфиг с токеном находится вне репозитория и монтируется только в контейнер туннеля; HTTP inspection выключен.

## Приёмка

1. Оба Compose-файла проходят `docker compose config --quiet`; Brev-конфиг требует `TYUIN_IMAGE`.
2. Образ собирается, контейнер переходит в `healthy`, отдаёт интерфейс и API.
3. `verify` подтверждает 2 248 ролей, 88 кластеров и 20 приоритетных узлов; три CSV доступны через API одного снимка.
4. Существующие тесты проходят в контейнере; после перезапуска основной сценарий работает.
5. Инструкция различает локальную проверку, выполненный облачный запуск и непроверенные способы публикации. Локальный запуск без Brev сохраняется.
6. На Brev проверены сборка из архива commit `3c6b1cd`, доступ к интерфейсу через SSH-туннель, API и выгрузки, существующие тесты и повторный запуск контейнера.
7. Предыдущий вариант с закреплённой HTTPS-ссылкой ngrok проверен без входа в Brev: API и три CSV совпадали со снимком приложения, перезапуск контейнера туннеля сохранял адрес. Без домена Compose отклоняет запуск вместо выдачи случайного URL. После перехода на собственный домен туннель остановлен.
8. `https://hackalemai.uniqore.dev` открывается с доверенным сертификатом Let's Encrypt; HTTP отвечает перенаправлением 308 на HTTPS. Проверены поиск по `gid`, API, объяснения, совпадение SHA-256 трёх CSV, перезапуск Caddy с последующим `/api/health` и отключение прежнего ngrok-туннеля. Код приложения остаётся на commit `3c6b1cd`; ранее прошедшие 29 тестов не запускались повторно для изменения HTTPS-прокси.

Инструкция и результаты проверки: [деплой на Brev](../deployment/brev.md). До локальной приёмки задача остаётся в разделе «В работе».
