# Реализовать демо-сценарий UX строго по ТЗ кейса

Статус: запланировано; реализация и приёмка не выполнены. [Бэклог](../backlog.md).

## Задача
Как AML-аналитик, я хочу пройти в интерфейсе путь от исходной выгрузки до обоснованного списка клиентов для проверки, чтобы воспроизводимо показать весь сценарий и выполнить проверки из ТЗ кейса.

Приоритет: наивысший — первая задача в очереди бэклога. Объём расширен от репетиции защиты до реализации UX-сценария с последующей проверкой. Эта запись не означает начало реализации.

## Основание и границы

Источник — [сохранённое ТЗ именно кейса «Граф денег»](../finance/sources/case.pdf): раздел 3 «Ключевой сценарий», разделы 5 и 7 (результаты и способы проверки), раздел 10 (демо). При расхождении с пересказом первичен PDF. Общий регламент хакатона и отдельные критерии Demo Day не подменяют эти требования.

Необходимый сценарий: исходный список из 81 клиента и предоставленные Parquet → обработка → сеть с направлениями, ролями и кластерами → топ-лист с основаниями → выбор клиентов для углублённой проверки. Интерфейс должен проводить аналитика по этому пути и позволять разбирать произвольный gid, без заранее зашитых «правильных» ответов.

## Соответствие UX и проверки требованиям ТЗ

| Требование кейса | Что реализовать или довести в UX | Как принять |
|---|---|---|
| Раздел 3: входные данные и построение сети | Понятный вход в работу с предоставленным набором; показать, какой набор обработан, и результат запуска. Команда запуска описана рядом в документации | На чистой машине одна команда из README обрабатывает исходные Parquet без ручных промежуточных шагов; три CSV готовы менее чем за 300 секунд |
| Разделы 3 и 5: схема сети | Просмотр направлений переводов, ролей и кластеров с переходами к выбранному клиенту и его связям | По названному жюри gid найти клиента и показать связи; отсутствие связей отображается честно |
| Раздел 7, пункты 2–3: роли и объяснимость | Доступные из выбранного клиента основная роль, оценка её поддержки, конкретные метрики, правила/пороги и ограничения вывода | Все 2 248 узлов присутствуют, обязательные поля заполнены; роли трёх произвольных gid объяснены за одну минуту |
| Раздел 7, пункт 4: группы | Просмотр группы: состав, размер, число seed, внутренний оборот и гипотеза | `clusters.csv` заполнен, у каждого узла указан `cluster_id`; интерфейс согласован с выгрузками |
| Раздел 3 и раздел 7, пункт 5: очередь проверки | Понятный топ-лист минимум из 20 клиентов с основаниями приоритета и переходом к разбору каждого | Аналитик понимает, кого проверять первым и почему, и может сформировать перечень для углублённой проверки; `top_nodes.csv` согласован с экраном |
| Раздел 10: демонстрация | Сквозной маршрут без тупиков между результатом запуска, сетью, группами, приоритетами, объяснениями и тремя выгрузками | Пять минут живого демо с содержательным разбором 2–3 узлов; одна схема «данные → метрики → роли → интерфейс» |

ТЗ не предписывает расположение панелей, пошаговый мастер или загрузку файлов через браузер. UX-решение выбирается при реализации; новый механизм загрузки собственных данных остаётся отдельной задачей бэклога. Для кейса нужен проход на предоставленных исходных файлах, без обязательного платного сервиса и аккаунтов команды.

Пять минут на полный пересчёт и пять минут на демонстрацию — разные ограничения. Для демо предусмотреть время на живой запуск и объяснения. Номера для проверки жюри произвольные; подготовленные 2–3 примера не заменяют эту проверку.

Связанные задачи по [гипотезам кластеров](cluster-purpose-hypotheses.md) и [основаниям приоритета](priority-explanations.md) сохраняются отдельно. Использовать их результаты или явно фиксировать недостающие части; не объявлять демо соответствующим ТЗ, пока обязательные основания отсутствуют.

## Что ещё не подтверждено
Сценарий демонстрации подготовлен, но успешная репетиция командой не зафиксирована. ТЗ предусматривает:
- объяснение ролей трёх произвольных gid за одну минуту на основе своих метрик;
- поиск названного gid на схеме и показ его связей;
- пятиминутное демо с живым запуском и содержательным разбором 2–3 узлов.

Аудит 23.09.2026 повторно проверил пайплайн и тесты, но не повторял живую проверку браузера и выступление команды.

## Что сделать
- Сопоставить текущий интерфейс с таблицей выше и зафиксировать разрывы пользовательского пути.
- Реализовать недостающие переходы, действия и объяснения, чтобы основной сценарий проходился в интерфейсе на реальных результатах расчёта.
- Обновить [сценарий демо](../finance/demo.md), README и схему решения под фактически реализованный путь; дополнительные AI-функции не должны мешать обязательному маршруту.
- Зафиксировать commit и окружение кандидата на сдачу.
- Повторно пройти локальный интерфейс: поиск полного gid, направления, роли, кластеры, досье, связи и три выгрузки.
- Провести репетицию по секундомеру: живой запуск, разбор 2–3 узлов, результат для аналитика и ограничения.
- Отдельно выбрать три gid без предварительного подбора удобных примеров и объяснить роли за одну минуту.
- Зафиксировать фактические времена, результаты и затруднения; скорректировать сценарий и повторить затронутые шаги при необходимости.

## Критерии готовности
- [ ] UX реализует весь путь из раздела 3 ТЗ; пункты таблицы соответствия проверены на одной версии, реализация отделена от планов.
- [ ] Сеть, группы, топ-лист, объяснения и CSV согласованы; все 2 248 клиентов учтены, минимум 20 приоритетов обоснованы.
- [ ] README, сценарий демо и одна схема решения соответствуют реализованному поведению; показ не требует заранее выбранных «правильных» gid.
- [ ] Живой запуск от исходных Parquet до трёх CSV выполняется одной документированной командой менее чем за 300 секунд, без обязательного платного сервиса и аккаунтов команды.
- [ ] Пятиминутный сценарий пройден с содержательным разбором 2–3 узлов.
- [ ] Три произвольных gid объяснены за минуту через правила, пороги и фактические метрики.
- [ ] Названный gid находится в интерфейсе; показаны направления и связи. Изолят корректно отображается без вымышленных связей.
- [ ] Дополнительно проверены пограничный узел и изолированный seed; ограничения наблюдения объясняются явно.
- [ ] Не заявляются accuracy без разметки, виновность клиента, измеренная экономия времени аналитика или непроверенная производительность на миллионе узлов.
- [ ] Отчёт содержит commit, окружение, команды/сценарии, фактические результаты и оставшиеся ограничения. Результат репетиции не выдаётся за подтверждение пользователя на merge.
