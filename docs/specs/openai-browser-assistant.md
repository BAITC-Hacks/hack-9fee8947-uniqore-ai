# Чат с OpenAI по данным выбранного клиента

Статус: выполнено. 23.09.2026 пользователь подтвердил локальную приёмку версии `dcc6017` и разрешил публикацию и слияние в `main`. Задача перенесена в [завершённые](../done.md). Живой запрос с настоящим ключом отдельным агентским прогоном не проверялся; технические результаты и ограничения зафиксированы в [отчёте](../finance/openai-assistant-validation.md).

## Задача и границы

Как AML-аналитик, я хочу задавать вопросы по данным и выводам аналитики в чате с LLM и получать ответы с опорой на исходные данные, чтобы быстрее уточнять выводы и проверять гипотезы.

Свободный чат объясняет уже рассчитанные факты выбранного клиента. Ассистент не меняет роли, оценки, граф, перечень проверки или CSV и не выполняет автономных действий. Основной анализ и три локальных объяснения доступны без ключа и внешнего AI. Аналитик самостоятельно проверяет ответ по досье; LLM не устанавливает виновность и не восполняет ненаблюдаемые данные.

## Ключ и пользовательский сценарий

1. При открытии вкладки «Ассистент» без ключа появляется окно ввода OpenAI API key. Его можно закрыть и использовать локальные объяснения.
2. До подтверждения ввода окно сообщает: ключ используется в браузере, не отправляется на сервер Tyuin и не сохраняется приложением; после перезагрузки страницы ключ нужно ввести снова. При отправке вопроса ключ используется для авторизации прямого запроса в OpenAI.
3. Предупреждение отдельно поясняет передачу вопроса, истории текущего диалога и ограниченного контекста выбранного клиента в OpenAI. Обещание об отсутствии сохранения относится к Tyuin, а не ко всем системам провайдера.
4. После ввода интерфейс явно показывает «Ключ задан» и действие удаления. Ввод не считается успешной проверкой доступа: она происходит при первом запросе. Полный ключ не отображается в статусе.
5. С заданным ключом доступны поле вопроса, отправка, состояние ожидания, ответ и понятные ошибки доступа, лимитов или сети. Неуспешный запрос не выдаётся за ответ AI; локальные объяснения остаются доступны.
6. Удаление ключа отменяет текущий запрос и очищает ключ, историю и состояние ответа. Поздний ответ удалённой сессии не появляется в интерфейсе.
7. При смене клиента или уходе с вкладки текущий запрос отменяется, история очищается. Ключ остаётся в памяти страницы до удаления или перезагрузки; новый клиент получает отдельный пустой диалог.

## Контракт интеграции

Frontend отправляет запрос непосредственно на фиксированный `https://api.openai.com/v1/responses`, модель — `gpt-4.1-mini`, параметр — `store: false`. Ключ передаётся в заголовке авторизации только этому endpoint. URL провайдера не редактируется пользователем. Новый чат не использует backend-прокси и серверные `LLM_*` как резервный источник ключа.

Автоматический контекст ограничен агрегатами и объяснениями выбранного клиента: роль, приоритет, основания, наблюдаемая активность и ограничения выборки. Вместо исходного gid используется нейтральное обозначение клиента; исходные операции, полный граф и чужие досье автоматически не передаются. Пользовательский вопрос и история передаются как текст: если аналитик сам вводит идентификатор или другие сведения, они входят в запрос. История ограничена и хранится только в памяти текущего диалога.

Ключ и чат не записываются в `localStorage`, `sessionStorage`, IndexedDB, cookies, URL, файлы или серверные журналы Tyuin. Ошибки не должны выводить ключ или необработанное тело ответа провайдера. Приложение не обещает управлять сохранением данных расширениями браузера, сторонними менеджерами паролей или OpenAI.

В раскрываемом блоке «Локальные пояснения · без API» ответы на «Почему эта роль?», «Почему этот приоритет?» и «Каких данных не хватает?» собираются frontend из уже загруженных фактов; они не вызывают backend LLM. Существующий `POST /api/nodes/{gid}/explain` сохраняется для внешних API-клиентов вместе с прежней серверной конфигурацией, но интерфейс ассистента его не использует.

Использование Responses и отключение сохранения ответа описаны в [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/migrate-to-responses), совместимость модели — на странице [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini). `store: false` не является обещанием полного отсутствия хранения у провайдера: обработка и журналы регулируются [условиями работы с данными OpenAI](https://developers.openai.com/api/docs/guides/your-data).

## Критерии приёмки и проверки

Техническая проверка описана в [отчёте](../finance/openai-assistant-validation.md). Точный проверяемый commit фиксируется в описании PR.

- [x] Открытие вкладки без ключа показывает окно с предупреждением; закрытие не блокирует локальные пояснения.
- [x] Заданный ключ виден как статус, доступно удаление; его ввод сам по себе не отправляет платный запрос и не утверждает, что доступ проверен.
- [x] Вопрос с ключом уходит только на фиксированный OpenAI endpoint с выбранной моделью и `store: false`; ключ отсутствует в теле и обращениях к серверу Tyuin.
- [x] Автоматический контекст ограничен выбранным клиентом и не содержит исходные gid, операции или полный граф.
- [x] Успешный имитированный ответ, отказ в доступе, лимит, недоступность сети, некорректный ответ и отмена дают корректное состояние интерфейса.
- [x] Удаление ключа, смена клиента и уход со вкладки отменяют запрос и исключают показ устаревшего ответа.
- [x] Перезагрузка очищает ключ и чат; браузерные хранилища не используются.
- [x] Локальные объяснения не обращаются к backend LLM даже при заданных серверных `LLM_*`; обязательная аналитика и CSV сохранены.
- [x] Проверены сборка frontend, связанные автоматические тесты и основной браузерный сценарий с имитацией OpenAI; команды и результаты записаны для проверенного commit.
- [x] Пользователь подтвердил локальную приёмку `dcc6017` и разрешил публикацию и слияние в `main` 23.09.2026.

Имитированные ответы проверяют контракт и жизненный цикл UI, но не доступность модели для конкретного ключа, квоты, списания, поведение реальной сети или качество живых ответов. Живой запрос требует отдельного фактического прогона с ключом пользователя; его отсутствие явно указывается в результате проверки.

## Проверка предложения по протоколу разработки

Объём — дополнительный ассистент, исходная версия — актуальная `main` перед веткой `feat/openai-browser-assistant`. Обязательные результаты кейса по-прежнему рассчитываются локально и не требуют аккаунта команды. Условия организатора и исходные данные не меняются.

По техническим критериям предложение сохраняет соответствие кейсу (вес 25), добавляет проверяемый контракт UI/API в реализацию (25) и воспроизводимый сценарий в README (25); ценность (15) — уточнение уже рассчитанных оснований. По потенциалу и оригинальности (10) заявляется только расширение интерфейса, без доказательств превосходства. Это веса организатора, а не полученные баллы. Для Demo Day проверяется понятность демонстрации ввода, удаления и утраты ключа после перезагрузки; баллы по отдельной шкале не выставляются.

Рекомендация по предложению: реализовать с проверкой имитированных запросов, затем показать локальную версию пользователю. Остаточный риск — ответ LLM может содержать ошибку, а живой доступ OpenAI ещё не проверен. Итоговое review должно опираться на фактические результаты реализации и не заменяет подтверждение локальной приёмки. Порядок работы — [протокол разработки](../development-workflow.md).
