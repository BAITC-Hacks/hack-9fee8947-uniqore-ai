# План внедрения agentic SDD

Этот план внедряет процесс работы Codex/Claude Code поверх общего плана Романа. Он не содержит задач реализации AML-продукта. Состояние сейчас: документация и templates подготовлены; пилот и автоматический runner не выполнены.

## Этап A Готовый процесс для текущего хакатона

| Задача | Владелец | Выход | Gate / проверка | Оценка |
|---|---|---|---|---|
| SDD-01 | Роман + пользователь | Путь/SHA общего плана, ограничения, integration owner | PA-01 | 5 мин после готовности плана |
| SDD-02 | Spec Author | R/AC/C и OPEN вопросы одной первой функции | PA-02 | 10–15 мин с агентом |
| SDD-03 | Coordinator | Task DAG, ownership, worktrees и baseline | PA-03/04/05 | 5–10 мин |
| SDD-04 | Worker + другой Reviewer | Один полный пилот с фактическим evidence | PA-06/07/19 | Входит во время первой продуктовой задачи |
| SDD-05 | Integrator | Проверенный candidate SHA и handoff | PA-10/11/15 | Входит в приёмку функции |
| SDD-06 | Coordinator | Краткая ретроспектива и корректировки процесса | Метрики acceptance.md | 5 мин |

Временной overhead SDD должен быть ограничен первыми 20–30 минутами setup и короткой карточкой/проверкой на каждую задачу. Это плановый бюджет, а не измеренный результат. Если общий план ещё не готов, можно подготовить templates и проверить инструменты; нельзя выдумать продуктовые задачи за Романа.

Первые 20–30 минут не добавляются поверх пяти часов: команда закладывает их внутрь общего расписания. При нехватке времени уменьшаем детализацию второстепенных отчётов, но не убираем требования, независимую проверку или evidence.

### Бюджет одного запуска: 300 минут

Это рамка процесса, которую Роман совмещает со своим продуктовым расписанием. Если часть пяти часов уже прошла, используется реальное оставшееся время; подготовка документа не обнуляет таймер.

| Минуты от начала | Работа | Правило выхода |
|---|---|---|
| 0–30 | Intake, первый spec baseline, task packets, worktrees | Одна READY задача; остальные детали уточняются по мере готовности |
| 30–75 | Первая вертикальная задача, independent review, integration | Один принятый результат с candidate SHA; фиксируем overhead |
| 75–210 | Независимые задачи по DAG, максимум два worker; review и integration входят сюда | Новую задачу брать, только если она укладывается вместе с проверками |
| 210–240 | Feature freeze; интеграция последних готовых задач | Новые функции не запускаются; только исправления принятого scope |
| 240–285 | Резерв полного acceptance, исправлений и проверки демо | На каждый новый commit повторяются затронутые и обязательные общие checks |
| 285–300 | Handoff: итоговый SHA, результаты, ограничения, подготовка передачи | Непринятые задачи явно отмечены; публикация по имеющейся авторизации |

Первые 30 минут — предел setup, а не предел всей координации: reviewer/integrator работают внутри следующих интервалов. При отставании Coordinator показывает прогноз и предложенное сокращение необязательных задач владельцам. Убрать обязательное требование без их решения нельзя; если оно не выполнено к сроку, результат обозначается неполным. Нельзя экономить время, выдавая непроверенное за DONE.

## Этап B Необязательная автоматизация после хакатона

Решение о выполнении этапа B принимается отдельно и только при измеренном bottleneck: повторные ручные передачи/расхождения статусов занимают существенную долю времени нескольких задач. Успех текущего пилота — одна принятая вертикальная функция, её время до интеграции и измеренная доля координации; он сам по себе не обязывает строить runner. Для пятичасового кейса этап B не является prerequisite и не должен конкурировать с продуктом. Плановая оценка 4–8 часов с coding agents после определения CLI; фактическая оценка уточняется пилотом, без обещаний скорости.

```text
validate artifacts -> claim task -> prepare packet -> invoke adapter
       ^                                      |
       |                                      v
 resume from ledger <- evidence <- bounded worker/reviewer cycle
       |
       v
single integration queue -> verify candidate -> human handoff
```

| ID | Компонент | Поведение | Зависимости | Приёмка |
|---|---|---|---|---|
| AUTO-01 | Validator | Схемы JSON, refs, DAG, ownership, версии, запрещённые пути | templates + процесс v1 | PA-01..04/21/24 |
| AUTO-02 | Ledger | Один writer, control branch, event seq, atomic persist, lease, resume | AUTO-01 | PA-09/12/20/22 |
| AUTO-03 | Git workspace adapter | Изолированный worktree, base/dependency check, scope diff, merge ancestry | AUTO-01 | PA-05/08/15/16/23 |
| AUTO-04 | Agent adapter | Интерактивная передача либо проверенный headless CLI | реальный tool preflight | PA-13/14/18 |
| AUTO-05 | Check/review gate | argv без shell, timeout, exit/SHA, reviewer independence | AUTO-02..04 | PA-06/07/09/19 |
| AUTO-06 | Integration/handoff | Последовательный candidate, actual tests, authorization gate | AUTO-05 | PA-10/11/17 |

Предлагаемый runner: обычный локальный Python CLI с JSON-артефактами и Git subprocess; окончательное решение проверяется на пилоте. Новые API keys не обязательны: adapters используют разрешённые coding environments. CLI flags и auth берутся из реально установленной версии и официальной документации при реализации, не из предположения этого плана.

Целевой интерфейс runner, которого пока нет:

```text
python tools/sdd.py validate --feature <feature-id>
python tools/sdd.py next --feature <feature-id>
python tools/sdd.py verify --task <task-id>
python tools/sdd.py status --feature <feature-id>
python tools/sdd.py resume --run <run-id>
```

Команды не включают auto-push/deploy. Операции apply/commit/integrate в автоматическом режиме требуют утверждённой политики конкретного run; проверка docs без запуска является read-only.

## Передача Роману

Роман определяет место общего плана в репозитории и интеграционную ветку. Наш pipeline принимает этот путь и revision в inputs.json; не создаёт конкурирующий product spec с собственными решениями. При разногласиях Coordinator передаёт только OPEN ID, влияющие задачи и варианты, без длинного transcript.

На выходе Роман получает task commits и review evidence для интеграционного candidate. Он может менять общую архитектуру: pipeline выполнит impact map и вернёт зависимые задачи на пересмотр. Workflow не становится препятствием для изменения курса, но делает последствия изменения видимыми.

## Очередь и критический путь

```text
SDD-01 -> SDD-02 -> SDD-03 -> первая task -> review -> integration -> SDD-06
                        \-> независимая вторая task -> review ---------^
```

Shared contracts и зависимости имеют одного writer; UI/аналитика либо другие продуктовые ветки допускаются параллельно только после подтверждения соответствующего контракта Романом. Предварительные fixture полезны, но не считаются доказательством работы на реальных данных.

## Риски и восстановление

| Риск | Ранний сигнал | Действие |
|---|---|---|
| Нет общего плана | path/SHA пусты | WAITING_INPUT; готовим процесс, не продукт |
| Процесс съедает хакатон | setup дольше 30 минут | Использовать интерактивный режим, отложить runner |
| Agents правят одни файлы | overlap allowed_files | Разбить ownership либо сериализовать |
| Test зелёный на другом commit | SHA mismatch | STALE и повтор affected checks |
| Reviewer повторяет слова автора | нет независимого rerun | Другой reviewer/человек, verdict blocked |
| CLI/version/auth неизвестны | preflight не проходит | BLOCKED_TOOL либо явный interactive adapter |
| Бесконечные исправления | один finding повторяется | До двух repair attempts, затем решение человека |
| Конфликт integration | shared contract расходится | Остановить apply, вернуть владельцу; не терять worktree |

## Необязательные дальнейшие улучшения

Автоматические schema validation в CI после стабилизации формата; визуальная очередь задач при росте команды; сбор process metrics; reusable adapters для новых инструментов. Каждое улучшение должно сокращать измеренный friction, а не добавляться потому, что возможна ещё одна роль агента.
