# Autoplan review: процесс разработки

Объект review — этот пакет agentic SDD, а не архитектура финансового продукта. Премиса подтверждена пользователем: «Процесс разработки через Codex и Claude Code». Роман владеет общим планом продукта. Документация процесса подготовлена; запуск пилота и runner не выполнялись.

## Режим review

Применён `autoplan`: последовательность CEO → Design → Engineering → DX. Независимый reviewer — fresh-context subagent. Внешний Codex CLI в текущей среде недоступен, поэтому режим `subagent-only`; dual-voice и cross-model consensus не заявляются. Design пропущен: UI не создаётся, документация и будущий CLI относятся к DX. Артефакты review и test plan хранятся в этом пакете репозитория, чтобы передаваться вместе с веткой; глобальные пользовательские настройки не меняются.

## CEO: завершено

Независимое начальное review: 7/10, три замечания. P1: не хватало общего бюджета 300 минут; P2: не выбрана топология двух участников; P2: runner мог стать лишним проектом. Внесены timeline с freeze и резервом, same-host пилот с bundle-передачей для двух host, назначение пользователя Coordinator/Integrator и post-hackathon gate для runner по измеренной потребности. Повторная внешняя оценка после исправления не выполнялась.

Премисы: два человека, пять часов, coding agents, обязательный LLM продукта. Первые три ограничивают workflow, последнее передаётся Роману и не выбирает инструменты orchestrator. Наличие общего плана и headless CLI не предполагалось: вход остаётся WAITING_INPUT, интерактивный режим предусмотрен явно.

Проблема — разрыв между постановкой задачи агенту и доказанной готовностью интегрированного результата. Успех пилота — одна принятая вертикальная функция с воспроизводимым evidence; количество агентов не является метрикой. Процесс не обещает выигрыш скорости до измерения координационных расходов.

Альтернативы: один агент в общей ветке проще, но плохо отделяет ownership и независимую проверку; полноценный orchestration framework требует времени и обслуживания. Выбран небольшой протокол поверх существующих coding environments. Его обратимость сохраняется: Markdown, JSON и Git остаются понятными без runner.

Scope ограничен процессом и templates. Продуктовые требования, стек, модели и интерфейсы принадлежат общему плану Романа. Инфраструктура автоматизации вынесена за текущий хакатон и не конкурирует с обязательными функциями.

Пользовательский путь процесса: владелец передаёт план, worker получает ограниченный packet, reviewer возвращает проверяемые findings, integrator передаёт точный SHA. Узкое место — два человека должны успевать проверять и интегрировать, поэтому эти действия входят в бюджет задач. Новые функции прекращаются на отметке 210 минут.

Конкурентный риск: ручной task board может оказаться дешевле описанного протокола для двух участников. Пилот измеряет долю координации и время до принятия, а не доказывает превосходство заранее. Если отчётность тормозит работу, сокращаются второстепенные записи, но сохраняются AC, ownership и evidence.

Рост через шесть месяцев не является текущим обязательством. Возможные extensions: CI-validator и adapters после устойчивого формата, затем визуальная очередь при росте команды. Условие продолжения — повторяемая измеренная проблема, не доступность ещё одного агента.

## Engineering: завершено

Независимая начальная оценка: 7,5/10. Четыре findings: P1 самоподрывающая запись evidence; P2 неполный baseline в JSON; P2 неоднозначные состояния/resume; P2 неопределённая семантика merge. Все приняты и исправлены в плане: отдельная control branch, единый baseline_ref, конечный enum с reason_code и переходами восстановления, merge с сохранением ancestry. Для каждого добавлен сценарий PA-20..23; runtime-проверка этих обещаний остаётся частью пилота.

### Архитектура и существующее решение

До этой ветки tracked repo содержал только README, готовых orchestration-компонентов, test framework и API нет. Используем существующие Git worktrees и интерактивные coding environments; нового сервиса/БД не требуется. Критический поток и границы writer приведены в README, control/code разделение устраняет циклическую зависимость SHA от отчёта о его проверке.

Зависимости запускаются по DAG с frozen baseline; merge сохраняет source SHA для ancestry и restart. Единственный Integrator — сознательный предел параллелизма, достаточный для двух людей. Недоступность одного инструмента приводит к явному fallback на интерактивную среду либо BLOCKED_TOOL; изменения прав/авторизации не угадываются.

### Качество и сопровождение

Кода runner пока нет, поэтому оценивается контракт будущих компонентов, а не качество несуществующих функций. Один baseline_ref заменяет разрозненные версии в task/review/evidence; reason_code не расширяет state enum. Роли разделены по записи: Worker меняет code, Reviewer проверяет, Coordinator сохраняет артефакты и статусы, Integrator собирает candidate.

### Проверки

Test framework в исходном repo отсутствует; не вводим его ради Markdown. Текущая проверка — парсинг JSON, ссылки, traceability ID и Git diff; tabletop/пилот ещё не выполнены. При реализации runner матрица acceptance.md становится набором unit/integration сценариев, включая сбои между side effect и event, scope violation и stale evidence.

### Производительность

Основная стоимость — время модели, человека и проверок, не JSON/Git dispatch. Два worker, ограниченные repairs и ранний freeze предотвращают неограниченное расходование бюджета, но выигрыш скорости пока не измерен. Спекулятивные кэши verdicts и параллельные merge не добавляются: первым измеряется время READY→DONE и доля координации.

### Completion

Архитектура, качество, тесты и производительность рассмотрены. Четыре замечания закрыты изменением плана; runtime correctness не заявлена. Codepath/test map находится в acceptance.md, ошибки/восстановление — выше, исключённый scope — в process-spec.md.

## DX: завершено

Независимая начальная оценка: 6,5/10. Четыре P2: неоднозначный bootstrap worktrees, неполный Worker prompt, неописанные элементы JSON collections, отсутствие input/run lifecycle. Добавлены quickstart с таблицей веток и порядком фиксации baseline, общая шапка prompts и commit-before-checks, examples.md и contracts для вложенных объектов, отдельные input/run enum. Root README ведёт к пакету; повторная внешняя оценка исправленного DX не выполнялась.

### Восемь проходов DX

**Getting started.** Первоначальный quickstart давал роли, но не создание baseline/worktrees. Теперь путь воспроизводится через один bootstrap prompt и последовательный рецепт, второй worker добавляется только при готовой независимой задаче. Независимая исходная оценка времени до READY была 35–50 минут; целевые 20–30 минут после исправлений остаются гипотезой.

**API/CLI.** Основной интерфейс пилота — task packet, а не команда несуществующего runner. Формы baseline/check_results/tasks/events теперь заданы вместе со связанным примером и JSON argv с пробелом. Предложенный будущий CLI отдельно помечен как проект интерфейса; специфичные flags Codex/Claude Code не выдуманы.

**Errors.** Прослежены INPUT_PLAN_MISSING, BASELINE_MISMATCH и TOOL_UNAVAILABLE от причины до восстановления. Для каждого quickstart показывает ожидаемое сообщение, действие и ссылку на правило; дополнительные task reasons не смешиваются со status. При blocked не обещаются прошедшие тесты и не теряется сохранённый commit.

**Documentation.** Root README теперь открывает пакет, в его начале есть маршрут по tutorial/reference/checks. Участник может начать с quickstart, а точные типы найти в contracts; examples не выдаётся за исполнение. Пустые templates остаются честно DRAFT, production requirements не заполнены вместо Романа.

**Upgrade.** Версии формата процесса и продуктового baseline различаются. Активный run не получает молчаливую миграцию: сохраняется старый control commit, описывается mapping и перепроверяются gates. Автоматические migration scripts на этом этапе не требуются, поскольку runner и установленных старых версий ещё нет.

**Environment.** Проверяется реально доступный coding environment, а не наличие бренда в подписке. Control/worker/integration worktrees перечислены явно; при двух компьютерах передаются Git objects и evidence, пути разрешаются локально. CI/editor integration пока не нужна для интерактивного пилота, её нельзя объявлять готовой.

**Team handoff.** Здесь ecosystem — два участника и общий repo, а не новая публичная платформа. Владелец продукта отвечает на короткие OPEN-вопросы; Coordinator отвечает за packet, интеграцию и handoff. Открытие публичного community, платного сервиса или plugin marketplace не добавляет ценности текущему scope.

**Measurement.** Начало TTHW определено как bootstrap_started_at, конец — первый READY event. Отдельно измеряются ожидание входов, coordination и проверки, чтобы не сокращать полезную верификацию ради метрики. После первого интегрированного результата проводится пяти минутная ретроспектива; runner появляется только при подтверждённой повторяющейся проблеме.

## Общие выводы и отложенные задачи

CEO и DX независимо указали на цену координации: общий timeline дополнен процедурой старта и измерением времени. Eng и DX независимо обнаружили неоднозначность lifecycle/передачи artifacts: единый baseline_ref, конечные enum и examples устраняют разные трактовки одним протоколом. Это совпадение тем между фазами, не cross-model consensus.

Всего зафиксировано 18 решений: 2 основаны на явных ответах пользователя, 16 приняты в пределах планирования. Изменения пользовательского scope не предлагались после уточнения premise; отдельного спорного taste choice нет. 11 независимых findings внесены в план (CEO 3, Eng 4, DX 4); повторный независимый прогон исправленных документов не заявляется.

Агрегированный implementation backlog: SDD-01..06 — принять вход, выпустить spec, подготовить packet/worktrees, провести пилот/review/integration и ретроспективу. AUTO-01..06 — только после хакатона и измеренной потребности; конкретные компоненты и acceptance уже перечислены в implementation-plan.md. CI-validator, новые adapters и визуальная очередь отложены туда же; отдельный конкурирующий продуктовый TODOS не создаётся.

Статус: REVIEWED DRAFT, готов к пользовательскому принятию процесса. Документация проверяется как документация; готовность runtime или продукта не заявляется. Следующий содержательный вход — путь/commit плана Романа, после чего возможен SDD-01.

Проверка артефактов: пять JSON templates и четыре JSON-примера разобраны; 23 относительные Markdown-ссылки разрешаются; 14 требований процесса имеют ссылки на приёмку; определены 24 сценария PA без неизвестных ID. Baseline_ref одинаковой формы во всех четырёх передающих артефактах. `git diff --check` с настройками репозитория проходит; тестов runtime нет, поскольку реализация не входила в запрос.
